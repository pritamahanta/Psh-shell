

Q1. What is the responsibility of parser.c?

->  parser.c performs syntax validation for shell commands before execution. It checks whether the command follows the shell's grammar, 
    ensuring that pipes, redirections, separators, and command structures are valid. It only validates syntax and does not execute any commands.

Q2. Why do you parse before executing?

->  Parsing ensures the entire command is syntactically valid before any execution begins. 
    This prevents partially executing malformed commands and keeps the execution layer focused only on running valid commands.

Q3. What parsing technique have you used?

->  I implemented a recursive-descent style parser. Each function corresponds to one grammar rule, 
    making the parser modular, easy to understand, and straightforward to extend.

Q4. Why didn't you use strtok() for parsing?

->  strtok() is useful for tokenization but cannot validate grammar. My parser needs to detect invalid constructs such as consecutive pipes, 
    missing filenames after redirection, or incomplete commands, which requires grammar-based parsing.



skip_ws()


Q5. Why have a separate skip_ws() function?

->  Whitespace is insignificant in most parts of shell syntax. By centralizing whitespace handling in a separate function, 
    the grammar functions remain cleaner and avoid duplicating the same logic.

Q6. Why is whitespace skipped before almost every parsing step?

->  Users may write commands with arbitrary spaces or tabs. 
    Skipping whitespace ensures the parser accepts syntactically equivalent commands regardless of formatting.


word()


Q7. What is considered a "word" in your parser?

->  A word is any sequence of non-whitespace characters that does not contain shell operators such as 
    |, <, >, &, or ;. Words represent command names, arguments, or filenames.

Q8. Why stop parsing a word when an operator is encountered?

->  Operators have special syntactic meaning in the shell grammar. 
    Treating them as part of a word would make it impossible to distinguish between commands and shell syntax.

Q9. Why return false when no word is found?

->  Many grammar rules require a command or filename at a specific position. 
    Returning false allows higher-level parsing functions to detect syntax errors and reject invalid input.


Redirection Parsing


Q10. Why have separate functions for input and output redirection?

->  Input and output redirections have different syntax and semantics. 
    Separating them keeps each parsing function focused on one grammar rule and makes future extensions easier.

Q11. Why save the parsing position?

    size_t save = *i;

->  If parsing fails, the parser restores the original position so that higher-level grammar rules can continue correctly without consuming invalid input.

Q12. Why must a filename follow < or >?

->  Redirection operators are incomplete without a target file. Accepting commands like cat < or echo > would produce invalid shell syntax.

Q13. Why support both > and >>?

->  > overwrites a file, while >> appends to it. They represent two different shell operators, so the parser recognizes both forms.



atomic()



Q14. What does an atomic command represent?

->  An atomic command is the smallest executable unit in my shell. 
    It consists of a command name followed by zero or more arguments and optional input or output redirections.

Q15. Why must every atomic command begin with a word?

->  Every executable command requires a command name. Starting with a redirection or pipe without a command would produce invalid shell syntax.

Q16. Why repeatedly parse words and redirections?

->  Commands may contain multiple arguments and multiple redirections. The loop continues parsing until no further valid argument or redirection is found.



valid_cmd_seg()



Q17. What is a command segment?

->  A command segment is one or more atomic commands connected by pipes. It represents a complete pipeline.

Q18. Why require another atomic command after |?

->  A pipe connects the output of one command to the input of another. A trailing pipe without a following command is syntactically invalid.

Q19. How does your parser reject ls |?

->  After encountering |, the parser immediately expects another atomic command. If none exists, parsing fails and the command is rejected.

Q21. Why parse one command segment first?

->  Every valid shell command must begin with a command segment. 
    Once the first segment is validated, additional segments separated by ; or & can be processed.

Q22. Why allow multiple segments separated by ; or &?

->  Shells support sequential execution using ; and background execution using &. 
    The parser recognizes both separators as valid ways to connect command segments.

Q23. Why allow an optional trailing ; or &?

->  Some shells permit commands such as ls; or sleep 5&. 
    Allowing a trailing separator makes the parser more user-friendly and compatible with common shell behavior.

Q24. Why check that the input ends with '\0'?

->  After successfully parsing the grammar, there should be no unexpected characters remaining. 
    Reaching the null terminator confirms the entire input was syntactically valid.


Error Detection


Q25. How does your parser detect syntax errors?

->  Each grammar function returns a boolean indicating success or failure. 
    If any required grammar rule cannot be satisfied, parsing immediately fails and the shell reports a syntax error.


Q26. Will your parser reject consecutive pipes?

    ls || pwd

->  Yes. After the first pipe, the parser expects another atomic command. Since another pipe is encountered instead, parsing fails.


Q27. Will your parser reject missing filenames?

    cat <

->  Yes. The input redirection rule requires a filename immediately after <. Without one, parsing fails.

Q28. Will your parser reject commands beginning with a pipe?

    | ls

->  Yes. Every command segment must begin with an atomic command. Since the parser encounters a pipe first, validation fails.

Q29. Will your parser reject empty commands?

    ;;

->  Yes. Every separator must connect valid command segments. Empty segments are rejected by the grammar.


Design Questions



Q30. Why use boolean return values?

->  Parsing is essentially a sequence of success-or-failure decisions. 
    Returning a boolean keeps the control flow simple and allows higher-level grammar rules to stop immediately when an error is detected.

Q31. Why pass the parsing index by pointer?

->  Every grammar function consumes part of the input. 
    Passing the index by pointer allows each function to advance the shared parsing position as it successfully recognizes grammar elements.

Q32. Why restore the parsing position on failure?

->  Some grammar rules attempt to recognize optional constructs. If recognition fails, 
    restoring the previous position prevents partially consuming invalid input and keeps parsing consistent.



Important Questions

Q33. Why did you write a parser instead of simply splitting the command using strtok()?

->  "strtok() can split input into tokens, but it cannot verify whether those tokens form a valid shell command. 
    My shell needs to reject malformed inputs such as trailing pipes, missing filenames after redirection, 
    or consecutive separators before execution begins. A recursive-descent parser lets me express the shell grammar directly, 
    validate syntax cleanly, and keep parsing separate from execution.
