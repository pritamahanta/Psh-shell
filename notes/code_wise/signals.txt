


Q1. What is the responsibility of signals.c?

->  signals.c is responsible for signal management in the shell. It installs custom signal handlers, 
    tracks the current foreground process group, forwards terminal-generated signals like Ctrl+C and Ctrl+Z to foreground jobs, 
    and coordinates job control by converting stopped foreground jobs into managed background jobs.

Q2. Why don't you use the default signal behavior?

->  The default behavior of signals like SIGINT and SIGTSTP would affect the shell itself. Instead, 
    the shell intercepts these signals and forwards them to the current foreground job so that 
    interactive programs receive them while the shell continues running.

Q3. Why are fg_pgid and fg_name global?

    static volatile sig_atomic_t fg_pgid = -1;
    static char fg_name[256];

->  Signal handlers execute asynchronously and need access to the current foreground job without depending on local variables.
    Storing the foreground process group ID and command name globally allows both the execution module and the signal
    handlers to access the same information.

Q4. Why is fg_pgid declared as volatile sig_atomic_t?

->  sig_atomic_t guarantees that reads and writes are atomic with respect to signal handlers.
    The volatile qualifier prevents the compiler from caching the value in a register, 
    ensuring the handler always sees the latest value written by the main execution flow.

Q5. Why is fg_name not a sig_atomic_t?

->  sig_atomic_t is intended for simple integer values. fg_name is a character array used only for reporting job information after signal handling. 
    It is updated before the foreground job begins execution and read later outside the signal handler.

Q6. What happens when the user presses Ctrl+C?

->  The terminal sends SIGINT to the shell because the shell is the process currently handling terminal signals.
    My custom handler checks whether a foreground process group exists and forwards the signal to that entire process group using kill(-pgid, SIGINT).
    The shell itself continues running.

Q7. Why do you send the signal to -pg?

    kill(-pg, SIGINT);

->  A negative PID tells the kernel to send the signal to every process in the specified process group. 
    This ensures that all processes belonging to a foreground job, such as a pipeline, receive the signal together.

Q8. Why not send the signal to a single PID?

->  A foreground job may consist of multiple processes connected by pipes. Sending the signal to only one PID would leave
    the remaining processes running. Using the process group guarantees consistent behavior for the entire job.

Q9. What happens when the user presses Ctrl+Z?

->  The shell receives SIGTSTP. Instead of stopping itself, it forwards the signal to the foreground process group. 
    It then records that a stop event occurred by setting pending_tstp and storing the process group ID. 
    The actual job management is performed later outside the signal handler.

Q10. Why don't you call jobs_add() directly inside the signal handler?

->  Signal handlers should execute only async-signal-safe operations. Functions like malloc(), printf(),
    or complex data structure modifications are not signal-safe. Instead, the handler records a pending event using simple atomic variables, 
    and the main execution flow processes it later.

Q11. Why do you use a "pending" flag?

    pending_tstp = 1;

->  The pending flag acts as a deferred notification. The signal handler simply records that a foreground job was stopped. 
    Later, after returning to normal execution, the shell safely updates the job table and prints status messages.

Q12. Why is pending_tstp_pgid stored?

->  The shell needs to know which process group was stopped. Since the actual job insertion happens later,
    the handler stores the process group ID so it can be used safely outside the signal context.

Q13. What is signals_init() responsible for?

->  signals_init() installs all custom signal handlers required by the shell.
    It configures handlers for SIGINT and SIGTSTP using sigaction() and ignores SIGQUIT.

Q14. Why do you use sigaction() instead of signal()?

->  sigaction() is the POSIX-recommended interface for signal handling. It provides more predictable behavior,
    allows configuration of signal masks and flags, and avoids portability issues associated with the older signal() API.

Q15. Why do you call memset() on the sigaction structures?

->  struct sigaction contains multiple fields. Initializing it with zeros ensures there are no uninitialized values that could cause undefined behavior.

Q16. Why call sigemptyset()?

->  sa_mask specifies which signals should be blocked while the handler is executing. 
    Calling sigemptyset() means no additional signals are blocked beyond the one currently being handled.

Q17. Why ignore SIGQUIT?

->  SIGQUIT normally terminates the process and may produce a core dump.
    Interactive shells typically ignore it so that pressing Ctrl+\ does not terminate the shell itself.

Q18. What is the purpose of signals_set_fg_pgid()?

->  Before a foreground job begins execution, the shell records its process group ID and command name. 
    The signal handlers later use this information to determine where Ctrl+C and Ctrl+Z should be forwarded.

Q19. Why clear fg_name when pgid < 0?

->  A negative PGID indicates that no foreground job is currently running. 
    Clearing the command name prevents stale information from being reused accidentally.

Q20. Why expose signals_get_fg_pgid()?

->  Other modules, such as the shell shutdown logic, need to know whether a foreground job is currently running.
    Providing a getter avoids exposing the internal variable directly.

Q21. What is the responsibility of signals_handle_pending()?

->  signals_handle_pending() processes deferred signal events outside the signal handler.
    When a foreground job has been stopped, it safely adds the job to the shell's job table,
    updates its state, and displays the appropriate message to the user.

Q22. Why is signals_handle_pending() called after waitpid()?

->  waitpid() confirms that the foreground job has actually stopped. Once the shell returns to normal execution, 
    it is safe to update internal job structures and print messages. 
    Performing these operations after waitpid() avoids unsafe work inside the signal handler.

Q23. Why is printf() not used inside on_sigtstp()?

->  printf() is not async-signal-safe because it uses internal buffers and locking. Calling it from a signal handler can result in undefined behavior.
    My implementation delays all printing until execution returns to normal code.

Q24. Why do you use kill() inside the signal handler even though many functions are unsafe?

->  POSIX defines kill() as async-signal-safe. It performs a simple system call and is therefore safe to invoke directly from a signal handler.

Q25. Explain the complete Ctrl+Z flow in your shell.

->  When the user presses Ctrl+Z, the shell receives SIGTSTP. 
    The handler forwards the signal to the current foreground process group using kill(-pgid, SIGTSTP).
    Instead of modifying the job table inside the handler, it records a pending stop event. 
    After waitpid() returns and execution is back in a normal context, 
    signals_handle_pending() adds the stopped process group to the shell's job table, marks it as stopped, 
    and prints the corresponding job status.
