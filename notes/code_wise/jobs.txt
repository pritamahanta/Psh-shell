


Q1. What is the responsibility of jobs.c?

->  jobs.c is responsible for managing the shell's background jobs. It maintains the job table, assigns job IDs,
    tracks job states, detects status changes using waitpid(), and cleans up completed jobs.

Q2. What information does your shell store for each job?

->  Each job stores its job ID, process ID, process group ID, command name,
    execution state (running or stopped), and whether the job entry is currently active.

Q3. Why maintain a job table?

->  A shell may have multiple background jobs running simultaneously. 
    The job table provides a centralized data structure for tracking every active job, allowing commands like jobs, 
    fg, and bg to operate efficiently.

Q4. Why initialize every job as inactive?

    st->jobs[i].active = 0;

->  During initialization, the job table contains garbage values. 
    Marking every entry as inactive establishes a known initial state and allows future insertions to locate free slots correctly.

Q5. Why maintain next_job_id?

->  Job IDs are user-facing identifiers used by shell commands such as fg %1 or bg %2. 
    They are independent of operating system PIDs and provide a simple sequential numbering system for users.

Q6. Why use job IDs instead of PIDs?

->  Process IDs are assigned by the operating system and can be large or reused over time. Job IDs are managed by the shell,
    remain small and sequential, and provide a more convenient interface for users.

Q7. Why search for the first inactive slot?

    if (st->jobs[i].active) continue;

->  The job table has a fixed size. 
    Searching for the first inactive entry allows completed jobs to reuse existing slots without allocating additional memory.

Q8. Why does jobs_add() return the job ID?

->  Returning the assigned job ID allows the caller to immediately reference the newly created job,
    for example when printing messages like [1] Stopped vim.

Q9. Why copy the command string?

    strncpy(...)

->  The original command buffer may be modified or freed after execution. 
    Copying the command into the job table ensures the shell retains the correct command name for future status messages.

Q10. Why explicitly null-terminate the copied string?

->  strncpy() does not always append a null terminator when the source is too long. 
    Explicit termination prevents undefined behavior when printing the command later.

Q11. Why is pgid initialized to pid?

    st->jobs[i].pgid = pid;

->  Every new job starts with its first process acting as the process group leader. 
    Therefore, the process group ID initially matches the PID of the first child process.

Q12. Why is the initial state JOB_RUNNING?

->  When a background job is first created, it begins execution immediately. 
    Therefore, its initial state is running until the shell later detects that it has stopped or exited.



Job Monitoring

Q13. What is the responsibility of jobs_check()?

->  jobs_check() periodically checks whether any background job has changed state. 
    It detects completed, stopped, continued, or terminated child processes and updates the shell's job table accordingly.

Q14. Why doesn't the shell simply wait for every child?

->  Waiting normally would block the shell until a child finishes. 
    Background jobs are intended to run concurrently while the shell continues accepting user input, so non-blocking status checks are required.

Q15. Why use waitpid() instead of wait()?

->  waitpid() provides much greater control. It supports non-blocking operation, 
    waiting for specific children or process groups, and reporting stopped or continued processes, making it ideal for implementing job control.

Q16. Explain this call:

    waitpid(-1, &status, WNOHANG | WUNTRACED | WCONTINUED)

->  -1 means wait for any child process. WNOHANG prevents blocking if no child has changed state. 
    WUNTRACED reports stopped children, and WCONTINUED reports children that have resumed after receiving SIGCONT.

Q17. Why use WNOHANG?

->  WNOHANG allows the shell to check child status without blocking. 
    If no child has changed state, waitpid() immediately returns 0, allowing the shell to continue interacting with the user.

Q18. Why use WUNTRACED?

->  Without WUNTRACED, waitpid() would report only terminated children. 
    Job control also requires detecting when a foreground job is stopped using Ctrl+Z.

Q19. Why use WCONTINUED?

->  A stopped job may later resume after receiving SIGCONT. 
    WCONTINUED allows the shell to detect this transition and update the job's state back to running.

Q20. Why use a while loop around waitpid()?

->  Multiple child processes may change state before the shell checks them. 
    Calling waitpid() repeatedly ensures every pending status change is processed instead of only the first one.

Q21. Why search for the matching PID?

->  waitpid() returns only the PID of the child whose state changed. 
    The shell must locate the corresponding job table entry so it can update the correct job.


Job States

Q22. What states can a job have?

->  In my implementation, a job can be either running or stopped. Completed jobs are removed from the active job table.

Q23. Why update the state on WIFSTOPPED()?

->  When a process receives SIGTSTP, it is suspended but not terminated. 
    Updating its state allows the shell to resume it later using commands like bg or fg.

Q24. Why update the state on WIFCONTINUED()?

->  A previously stopped job may resume execution after receiving SIGCONT. 
    Updating the state keeps the job table synchronized with the actual process state.

Q25. Why remove completed jobs?

    st->jobs[idx].active = 0;

->  Once a job has terminated, it no longer needs to occupy a slot in the job table. Marking it inactive frees the entry for future background jobs.


Zombie Processes

Q26. Why call waitpid() even for background jobs?

->  When a child process exits, it becomes a zombie until its parent collects its termination status. 
    Calling waitpid() reaps the child and prevents zombie processes from accumulating.

Q27. What is a zombie process?

->  A zombie is a process that has already terminated but whose parent has not yet collected its exit status using wait() or waitpid(). 
    It no longer executes but still occupies an entry in the kernel's process table.

Q28. What happens if jobs_check() is never called?

->  Background jobs would remain as zombies after termination because the shell would never reap them. 
    Over time, the system's process table could fill with zombie entries.

Exit Status

Q29. Why distinguish between WIFEXITED() and WIFSIGNALED()?

->  A process may terminate normally by returning from main() or calling exit(), or it may terminate because of a signal such as SIGKILL or SIGSEGV. 
    Distinguishing these cases allows the shell to report more accurate status information.

Q30. Why use WEXITSTATUS()?

->  WEXITSTATUS() extracts the program's exit code from the status returned by waitpid(). 
    This allows the shell to determine whether the program completed successfully or reported an error.

Q31. Why flush stdout after printing job status?

->  Job completion messages may appear asynchronously with respect to the shell prompt. 
    Flushing stdout ensures the message is displayed immediately instead of remaining in the output buffer.



Design Questions


Q32. Why use a fixed-size job table instead of dynamic allocation?

->  A fixed-size table keeps the implementation simple, avoids dynamic memory management, 
    and provides predictable lookup time. It is sufficient for a teaching shell where the maximum number of concurrent jobs is bounded.

Q33. What happens if the job table becomes full?

->  jobs_add() cannot find an inactive slot, reports that the maximum number of background jobs has been reached, and returns -1, 
    preventing insertion beyond the table's capacity.

Q34. Why does jobs_check() ignore unknown PIDs?

    if (idx == -1) continue;

->  Some child processes may already have been removed from the job table or may not correspond to managed background jobs. 
    Ignoring unknown PIDs keeps the shell robust and avoids accessing invalid entries.
